# Criteria2Query 3.0：大语言模型用于临床试验筛选标准查询生成 中文翻译版

原文题名：Criteria2Query 3.0: Leveraging Generative Large Language Models for Clinical Trial Eligibility Query Generation

## 中文题名

Criteria2Query 3.0：利用生成式大语言模型生成临床试验筛选标准查询

## 摘要翻译

本文研究如何利用生成式大语言模型辅助临床试验 eligibility criteria 的查询生成。传统上，把自由文本筛选标准转成数据库查询需要大量人工工作，也需要研究者熟悉医学术语、数据模型和查询语言。

Criteria2Query 3.0 将大语言模型引入这个流程，希望提高筛选标准解析、查询生成和人机协作的效率。

## 方法翻译

这类 LLM 方法的基本思路是：

1. 输入自由文本筛选标准。
2. 让大语言模型理解医学条件。
3. 生成结构化查询或中间表示。
4. 通过规则、模板或人工审查修正模型输出。
5. 得到可执行的查询。

大语言模型的优势在于能较好理解复杂自然语言、医学表达和长句逻辑。但它的风险也很明显：可能编造字段、误解标准、生成不可执行代码，或者输出不符合目标数据模型的内容。

## 结果和结论翻译

LLM 路线说明，生成式模型已经可以参与 eligibility query generation，但可靠性和可验证性仍然是核心问题。临床研究任务不能只看语言生成是否流畅，必须看最终查询是否准确、可执行、可复现。

## 对 CHIP2026 的启发

这篇文章和我们的比赛非常相关，因为 CHIP2026 允许基于大语言模型生成 FHIR Bundle。

可借鉴路线：

1. 让 LLM 帮忙读 `question` 和 `FHIR_FSH`。
2. 让 LLM 生成 `NLP_CODE` 初稿。
3. 用程序检查语法、入口函数、base64 和 Bundle 格式。
4. 用 `FHIR_SERVICE_CODE` 反向校验生成的 Resource 字段。
5. 对每条题保留人工审查记录，保证可复现。

不要做：

1. 不要直接相信 LLM 输出。
2. 不要依赖联网 API 才能运行最终代码。
3. 不要生成平台环境没有的依赖。
4. 不要只看代码像不像，要实际检查能不能被查询代码查到。

大白话：

> LLM 可以当聪明助手，但不能当最终裁判。最终裁判是代码能不能跑、FHIR 对不对、查出来的人对不对。
